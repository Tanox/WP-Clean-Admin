## 1. 评估结论摘要

| 维度 | 结论（1.9.17 评估） | 1.9.18 实施后状态 |
|------|------|----------|
| 代码实现 | 模块化与 trait 治理完成度高；但存在**核心功能读写键不一致**与设置回显错误 | **已修复**：菜单定制统一单一数据源 + 无条件注册；字段回显改读嵌套设置 |
| 架构设计 | 引导链与模块装载清晰，safe_init 具备容错；错误处理器双注册、契约三套并存 | **已修复**：`Error_Handler` 唯一注册点；AJAX 统一 `Response` DTO |
| 性能 | 缓存/资源优化开关齐备；但设置读取无记忆化、缓存清理全表扫描、文件缓存每请求 glob | **已优化**：设置请求级记忆化；缓存分批 + cron；文件缓存原子写入并迁出插件目录 |
| 安全 | 输入消毒/nonce/权限/路径边界已建立；REST 限制注册时机错误、前端 `.html()` 插值 | **已修复**：REST 限制改 `rest_api_init` 注册；前端移除 `.html()` 与 `alert()` |
| 用户体验 | 五 Tab 设置页具备语义 ID；但重复字段、无 ARIA、alert 反馈、无进度 | **已修复**：每 Tab 独立 page slug 唯一渲染 + WAI-ARIA + 页面内状态提示 |

## 2. 优先级定义

| 优先级 | 含义 | 响应要求 |
|--------|------|----------|
| P0 | 核心功能不可用或数据错误 | 立即修复，补丁版本发布，须有回归测试 |

## 3. 功能正确性与接口契约

### OPT-001（P0）菜单定制器读写 option 键不一致且 AJAX 默认未注册

- **问题背景**：保存写入 `wpca_menu_customizer_settings`（`modules/admin/classes/class-wpca-menu-customizer-options.php:26,53`），渲染/导出却读取 `wpca_get_settings()` 即 `wpca_settings`（`class-wpca-menu-customizer-tree-customize-tasks.php:35`、`class-wpca-menu-customizer-render.php:34,143`），导入写回前者（`:169,175`）。4 个 AJAX action 被 `isset($settings['menu_customizer'])` 守卫（`class-wpca-menu-customizer.php:87-101`），而该键不在默认配置中（`wp-clean-admin.php:142-169`、`Core_Settings::get_default_settings():31-46`），默认注册数为 0。
- **实施方案**：技术选型——以 `Menu_Customizer_Options` 为唯一数据源，构造器注入 Tree/Render，避免全局 option 直读；步骤：①统一 `get_settings()` 为唯一入口；②AJAX action 无条件注册（校验已在 handler 内完成）；③默认配置补 `menu_customizer.enabled=false`；④提供从 `wpca_settings.menu_customizer` 到独立键的一次性迁移；⑤增加“保存→渲染→导出→导入”端到端测试。
- **预期效果**：默认注册 action 数 **0→4**；保存后定制项生效率 **0%→100%**；导入导出闭环恢复；回归测试覆盖 4 条关键路径。
- **实施优先级**：**P0**，须在补丁版本修复并验证。
- **实施状态（1.9.18 已完成）**：`Menu_Customizer_Options` 成为唯一数据源（`OPTION_KEY = 'wpca_menu_customizer_settings'`），Tree / Render / Customize-Tasks 通过构造器注入同一实例，统一经 `get_settings()` 读取、`save_settings()` 写入；`Menu_Customizer::init()` 移除 `settings['menu_customizer']` 守卫，4 个 AJAX action **无条件注册**；提供从 `wpca_settings.menu_customizer` 的幂等 legacy 迁移（不删除旧数据）。默认注册 action 数 **0→4**，保存后定制项生效。

### OPT-002（P1）AJAX 响应契约三套并存、设置 handler 未挂载

- **问题背景**：`settings-ajax.php` 返回 `{message:...}`（`includes/ajax/settings-ajax.php:31-63`），菜单定制器返回字符串载荷（`class-wpca-menu-customizer-ajax-tasks.php:34-44,72-74`），标准 DTO 在 `Helpers` 中已定义却未使用（`class-wpca-helpers-error-tasks.php:33-62`）；文档曾承诺统一结构（`docs/api-reference.md:34`）。全仓无 `wp_ajax_wpca_save/get/reset_settings` 注册，但菜单处理器依赖该文件的 `sanitize_settings()`（`:63`，自动加载见 `includes/autoload.php:84-87`）。
- **实施方案**：技术选型——新增 `WPCleanAdmin\AJAX\Response` 静态工厂（`success()`/`error(WPCA_Errors)`），底层统一 `wp_send_json`；步骤：①`Response` 落地并写契约测试；②四个菜单 handler 与设置 handler 全量迁移；③`sanitize_settings()` 下沉到 Helpers 以解除对未挂载类的耦合；④决策注册或删除 settings handler 并在 `openapi.yaml` 同步；⑤前端按 `error_code` 分支处理。
- **预期效果**：JSON 结构种类 **3→1**；可解析 `error_code` 的错误路径 **0→全部**；消除“死 handler + 活依赖”耦合。
- **实施优先级**：**P1**，与 OPT-001 同批处理可减少回归成本。
- **实施状态（1.9.18 已完成）**：新增 `WPCleanAdmin\AJAX\Response`（`includes/ajax/response-ajax.php`）作为统一响应工厂（`success()` / `error()`，底层 `wp_send_json`）；4 个菜单定制 handler 全部迁移至该 DTO，错误响应统一携带 `error_code`；`sanitize_settings()` 递归消毒下沉至 `Helpers`（`class-wpca-helpers-validation-tasks.php`），`AJAX\Settings` 仅保留静态代理；原 3 个从未注册的 `save/get/reset_settings` handler **已删除**，消除「死 handler + 活依赖」耦合。JSON 结构种类 **3→1**。

### OPT-003（P1）设置字段回显读取错误 option 键

- **问题背景**：`Settings_Fields::render_field()` 对每个字段执行 `get_option($args['id'])`（`modules/admin/settings/class-wpca-settings-fields.php:112-118`），但实际保存路径为 `register_setting('wp-clean-admin','wpca_settings')` 与嵌套结构（`class-wpca-settings-registration-tasks.php:81-83`、`class-wpca-settings-validation.php:35-43`、`includes/ajax/settings-ajax.php:55`）。当前 4 个已注册字段回显均可能错误。
- **实施方案**：技术选型——以 `wpca_get_settings()` 为唯一读源，按分组键路径取值；步骤：①`render_field()` 改为 `wpca_get_settings()['general'][$id] ?? get_option($id,$default)`；②按字段类型应用白名单消毒；③补“保存→刷新→回显”回归测试；④同步修正 `docs/FAQ与故障排除.md` 中该现象描述。
- **预期效果**：字段回显正确率 **0%→100%**；用户“保存无效”工单预计显著下降。
- **实施优先级**：**P1**。
- **实施状态（1.9.18 已完成）**：`Settings_Fields::render_field()` 改为优先读取嵌套结构 `wpca_settings[group][id]`（嵌套优先，缺失时回退独立 option），并以 `array_key_exists` 判定以保证 `0` / `false` 等假值正确回显；字段 `name` 属性同步输出为 `wpca_settings[group][id]`；新增 `group` 字段标识与 `esc_textarea` / `checked` / `selected` 测试桩；补充「保存→刷新→回显」回归用例（`tests/SettingsFieldsEchoTest.php`）。

## 4. 架构与错误处理

### OPT-004（P1）两套全局错误处理器并存，其中一套吞掉所有 PHP 错误

- **问题背景**：`Core\Classes\Error_Handler` 注册 `set_error_handler`/`set_exception_handler`/shutdown（`modules/core/classes/class-wpca-error-handler.php:80-92`）；Helpers 另提供 `register_error_handler()`（`class-wpca-helpers-error-tasks.php:121-124`），其 `custom_error_handler()` 对已报告错误一律 `return true`（`:135-170`），阻止默认输出与处理器链；两者日志目标不同（`class-wpca-file-logger.php:32-61`）。
- **实施方案**：技术选型——保留 `Error_Handler` 为唯一注册点，Helpers 仅负责响应 DTO；步骤：①废弃/降级 `register_error_handler()`；②无法处理的错误返回 `false` 或显式 chaining；③统一日志通道与严重级别；④补错误注入测试（触发 E_WARNING 与异常各一次）。
- **预期效果**：全局处理器 **2→1**；被静默吞掉的错误类别降至 **0**；日志定位时间缩短。
- **实施优先级**：**P1**。
- **实施状态（1.9.18 已完成）**：`Helpers::register_error_handler()` 降级为 deprecated no-op（保留签名兼容）；`custom_error_handler()` 对已报告错误返回 `false`（交回 PHP 默认处理与处理器链，**不再吞错**）；`Error_Handler` 增加 `private static $registered` 防止重复注册，全局处理器 **2→1**，日志统一写入 `Error_Handler` 注册的全局通道。

## 5. 安全有效性

### OPT-005（P1）“禁用 REST API”在纯 REST 请求上不生效

- **问题背景**：`rest_authentication_errors` 仅在 `optimize_frontend_resources()` 中添加（`modules/utilities/classes/class-wpca-resources-optimization-tasks.php:57-59`），而该方法挂 `wp_enqueue_scripts`（`class-wpca-resources.php:63`）；`/wp-json` 请求不触发脚本入队。回调仅拦截未登录用户并返回 401（`:112-119`），与规格“仅认证用户可访问”的状态码语义不一致。
- **实施方案**：技术选型——在 `rest_api_init`（或 `plugins_loaded`）注册过滤，必要时辅以 `rest_pre_dispatch`；步骤：①迁移过滤注册点；②未登录返回 `WP_Error('rest_not_logged_in', ..., ['status'=>403])` 与规格对齐；③补真实 HTTP 集成测试（匿名/登录各一）；④在 `docs/API接口文档.md` 与用户指南更新行为说明。
- **预期效果**：匿名 REST 请求拦截率在当前路径下 **0%→100%**；状态码语义与规格一致；误配置导致的绕过风险消除。
- **实施优先级**：**P1**（安全开关实效性）。
- **实施状态（1.9.18 已完成）**：REST 限制过滤改由 `Resources::init()` 的 `rest_api_init`（priority 1）注册 `rest_authentication_errors`；匿名请求返回 `WP_Error('rest_not_logged_in', …, ['status' => 403])`，已登录用户与既有错误透传不拦截；纯 REST 请求路径的拦截率 **0%→100%**，状态码语义与规格对齐；新增 `tests/RestApiRestrictionTest.php` 覆盖匿名/已登录两条路径。

## 6. 性能与资源

### OPT-006（P1）数据库缓存清理无 LIMIT、N 次单删且无过期 cron

- **问题背景**：`SELECT option_name ... LIKE 'wpca_cache_%'` 无 LIMIT（`modules/utilities/classes/class-wpca-cache-database-tasks.php:103`），随后逐条 `delete_option`（`:105-107`）；过期仅在读取时检查（`:41-43`）；注释称“done via cron”（`class-wpca-cache-file-tasks.php:155`）但运行时无任何 `wp_schedule_*` 注册。
- **实施方案**：技术选型——`$wpdb->prepare` + 分批 `LIMIT 500` + WP-Cron 周期任务；步骤：①分批查询循环删除；②注册 hourly single event 清理过期项；③停用/卸载时 unschedule；④补大规模缓存项（≥1000）压测。
- **预期效果**：无界扫描与 N 次串行删除降为可控批次；过期项回收不再依赖被读取；大站清理耗时预计下降一个数量级（需实测）。
- **实施优先级**：**P1**。
- **实施状态（1.9.18 已完成）**：数据库缓存清理改为 `LIMIT 500` 分批查询 + 分批删除，过期项由 hourly WP-Cron 事件 `wpca_cache_cleanup` 兜底回收（停用/卸载时 unschedule）；无界扫描与 N 次串行删除降为可控批次。

### OPT-007（P1）文件缓存位于插件目录、每次初始化全目录 glob、写入非原子

- **问题背景**：缓存目录为 `WPCA_PLUGIN_DIR.'cache'`（`class-wpca-cache-file-tasks.php:137-146`）；`clear_file_cache`/`clean_expired_file_cache` 全量 `glob`（`:107,165`）；`Cache::init()` 每次实例化都清理（`class-wpca-cache.php:83-89`），而 Cache 每请求加载（`class-wpca-module-loader.php:111-119`）；`file_put_contents` 无 `LOCK_EX`/rename 原子替换（`:79`）。
- **实施方案**：技术选型——缓存迁至 `wp_upload_dir()['basedir'].'/wpca-cache'` 并加 `.htaccess`/`index.php` 防护；`FilesystemIterator` + cron 限频；写入用临时文件 + `rename()`；优先对象缓存后端；步骤：①新增路径服务并兼容旧目录读取；②清理改 cron hourly；③原子写入；④迁移脚本与回滚说明。
- **预期效果**：每请求 O(N) 文件 stat/JSON 解码 **→0**（清理由 cron 承担）；并发写撕裂消除；插件目录不再需要写权限。
- **实施优先级**：**P1**。
- **实施状态（1.9.18 已完成）**：文件缓存目录迁至 `wp_upload_dir()['basedir'] . '/wpca-cache'`，并写入 `index.php` 与 `.htaccess` 防护文件；写入改为临时文件 + `rename()` 原子替换；清理改由 hourly cron 限频承担（`FilesystemIterator` 遍历），不再每请求全目录 `glob`；插件目录不再需要写权限。

### OPT-008（P2）同一请求重复读取全量设置、无记忆化

- **问题背景**：`wpca_get_settings()` 每次调用都 `get_option('wpca_settings')`（`includes/wpca-core-settings-functions.php:24-31`）；登录样式流程 5 次（`class-wpca-login-style-enqueue-tasks.php:31,66,84,99,115`），菜单渲染 3 次（`class-wpca-menu-customizer-render.php:34,143,169`）。
- **实施方案**：技术选型——请求级静态 `Settings\Repository` 快照 + 写路径失效；步骤：①引入 Repository 并在 `wpca_get_settings()` 内缓存；②`wpca_update_settings`/AJAX 保存后失效快照；③逐步以构造器注入替代 trait 内重复读取；④用 profiler 对比前后调用次数。
- **预期效果**：登录相关流程设置读取 **5→1（-80%）**；菜单渲染 **3→1（-67%）**；DB 往返通常已由 WP 对象缓存降低，收益主要在内存与过滤开销。
- **实施优先级**：**P2**。
- **实施状态（1.9.18 已完成）**：`wpca_get_settings()` 增加请求级记忆化（`$GLOBALS['wpca_settings_cache']`），新增 `wpca_flush_settings_cache()` 显式失效入口；`wpca_update_settings()` 写后自动失效缓存，避免读到陈旧快照。

### OPT-010（P2）仪表盘同步执行重型全表统计查询

- **问题背景**：小部件渲染直接调用 `get_dashboard_stats()`（`modules/admin/classes/class-wpca-dashboard-widget-tasks.php:44`），含 `information_schema` 求和、前导通配符 `LIKE '%transient%'`、`postmeta`/`termmeta` 两次 LEFT JOIN（`class-wpca-dashboard-data.php:37-50`）。
- **实施方案**：技术选型——15 分钟 transient + WP-Cron 后台聚合 + AJAX 懒加载；步骤：①统计结果缓存；②`NOT EXISTS` 改写以利用索引；③小部件先渲染骨架再由 AJAX 填充；④大表站点压测对比首屏时间。
- **预期效果**：命中缓存时同步重查询 **4→0**；首屏关键路径不再包含全表扫描；大表站点首屏时间预计明显下降（需实测）。
- **实施优先级**：**P2**。
- **实施状态（1.9.18 已完成）**：仪表盘统计结果以 15 分钟 transient（`wpca_dashboard_stats`）缓存，命中时不再执行重型统计；transients 计数改用前缀匹配聚合，孤儿 meta 统计改写为 `NOT EXISTS` 以利用索引；命中缓存时同步重查询 **4→0**。AJAX 懒加载骨架未在本轮实施（前端改用页面内进度提示承载），登记为残留项见 `tasks.md`。

## 7. 用户体验与可访问性

### OPT-009（P1）设置页四个 Tab 重复渲染全部字段且缺少 ARIA 语义

- **问题背景**：4 个面板各自调用 `do_settings_sections('wp-clean-admin')`（`modules/admin/settings/class-wpca-settings-page.php:64-97`），而字段仅注册一组（`class-wpca-settings-fields.php:54-104`）→同名 id/name 重复；Tab 按钮无 `role="tab"`/`aria-selected`/`aria-controls`，面板无 `role="tabpanel"`（`:44-59,64-97`）；提示 div 无 `aria-live`（`:108`）；JS 仍向 `<head>` 注入 `<style>`（`assets/js/wpca-settings.js:227-236`）。
- **实施方案**：技术选型——WAI-ARIA Tabs 模式 + 每 Tab 独立 settings section/page slug；步骤：①按 Tab 注册并渲染各自 section；②按钮/面板补齐 ARIA 属性与键盘导航；③提示容器 `role="status" aria-live="polite"`；④内联 `<style>` 改为 `wp_enqueue_style`；⑤用 axe 或浏览器辅助功能检查验证。
- **预期效果**：重复输入 **16→4**（4 字段×4 面板 → 4）；4 个 Tab 全部具备可访问状态；内联 `<style>` **1→0**。
- **实施优先级**：**P1**。
- **实施状态（1.9.18 已完成）**：4 个 Tab 改用**独立 settings page slug**（`wp-clean-admin-general|cleanup|performance|security`）分别注册与渲染，同一字段不再跨 Tab 重复输出（重复输入 16→4）；Tab 按钮与面板补齐 WAI-ARIA（`tablist` / `tab` / `aria-selected` / `aria-controls` / `tabpanel`）；保存提示容器改为 `role="status" aria-live="polite"`；内联 `<style>` 从 JS 移除，迁至 `assets/css/wpca-settings.css`。

### OPT-011（P1）前端反馈依赖 alert、无进度且用 `.html()` 注入服务端文本

- **问题背景**：诊断结果将 `check.name/message/action` 直接 `.html()` 拼接（`assets/js/wpca-dashboard.js:74-83`）；错误与成功均用 `alert()`（`:89,116,119,124`）；清理按钮仅 “Processing...” 文本（`:99-101`）；设置页提示同样用 `.html()`（`wpca-settings.js:190-214`）。
- **实施方案**：技术选型——DOM API + `text()`/jQuery `.text()` + `wp.i18n` + `wp.ajax.post` 统一错误解析；步骤：①替换 4 处 `.html()` 插值；②提示改为 `role="status"` 页面内提示；③长操作分段进度条；④移除内联样式；⑤补 XSS 回归用例（服务端返回含 `<img onerror>` 字符串）。
- **预期效果**：未转义插值点 **4→0**；错误提示可本地化且可被读屏软件播报；长操作从 0 进度反馈→分阶段反馈。
- **实施优先级**：**P1**（UX + 潜在存储型 XSS）。
- **实施状态（1.9.18 已完成）**：`wpca-dashboard.js`、`wpca-settings.js`、`wpca-main.js` 移除全部 `alert()` 与 `.html()` 插值，服务端文本改经 jQuery DOM API `.text()` / `$('<span>').text()` 输出；错误与成功改为页面内状态提示（可被读屏软件播报）；长操作补内联进度/状态提示；原内联 `<style>` 迁至 `assets/css/wpca-settings.css`。未转义插值点 **4→0**。

### OPT-012（P2）测试/质量门禁与对外契约缺口

- **问题背景**：`composer test` 为裸 `phpunit`（`wpcleanadmin/composer.json:33-38`），`phpunit.xml.dist` 仅配置 coverage include、无阈值（`phpunit.xml.dist:14-18`）；CI 中 PHPCS `continue-on-error: true`（`.github/workflows/ci.yml:34-39`）；运行时无 REST 端点，OpenAPI 此前缺失；`docs/api-reference.md:34` 的响应结构描述与实际漂移。
- **实施方案**：技术选型——PCOV/Xdebug 覆盖率 + PHPCS 阻塞门禁 + OpenAPI 3.1（本批已补 `docs/openapi.yaml`）；步骤：①接入 `--coverage-text --min=70`；②规则集调优后移除 `continue-on-error`；③按需新增 `wpca/v1` REST 路由（含 `permission_callback`）并同步 `openapi.yaml`；④本批文档已补齐，后续每次公开接口变更须同步契约与 `API接口文档.md`；⑤`uninstall.php` 补 cron unschedule 与缓存目录清理说明。
- **预期效果**：覆盖率门禁 **0→≥70%**；PHPCS 由非阻断→强制；对外 REST 端点 0→可用且有机器可读契约；卸载残留目录 **≥2→0**（若同时落地目录清理）。
- **实施优先级**：**P2**（工程治理，可随版本渐进）。
- **实施状态（1.9.18 部分闭环）**：①新增覆盖率门禁工具 `tools/check-coverage.php`（解析 Clover 报告并校验总覆盖率阈值，默认 70%），composer 增加 `test:coverage` 脚本，CI 新增 `coverage` 作业（pcov），**首次以 `continue-on-error: true` 仅报告基线**，待实测基线确认后再转阻塞；②PHPCS 仍为非阻塞（规则集调优后移除 `continue-on-error`，见 `tasks.md` 残留项）；③`docs/openapi.yaml`（OpenAPI 3.1）已补齐并与 `docs/API接口文档.md` 同步；④`uninstall.php` 补充清理 WP-Cron 事件与文件缓存目录。**未新增 `wpca/v1` REST 路由**——本插件对外仍仅提供 AJAX，REST 端点保持「无」的设计取舍。残留项已登记 `tasks.md`。
